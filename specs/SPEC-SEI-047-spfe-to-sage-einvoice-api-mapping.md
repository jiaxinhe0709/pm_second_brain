# SPFE SOAP to Sage E-Invoice API Mapping

An authorised business needs to send, cancel or rectify Spain invoices, find and download them, report buyer or seller actions, and recover failed or uncertain requests. This reference maps the nine SPFE SOAP services to the existing Sage E-Invoice API surface. It links to the owning specifications for detailed fields, rules and acceptance checks.

**Proposed reuse direction:** retain the common Send, Query, Retrieve and status APIs, with qualified Spain rules and SPFE transport. Submission withdrawal has no documented equivalent in the supplied E-Invoice contracts. Service 09 is available only in sandbox/PRE and is excluded from the live production flow. Existing France contracts establish reuse candidates; deployed Spain implementation coverage remains unknown. REF-SND, REF-RCV, REF-LIF, REF-WITHDRAWAL; SPFE-S03 §6.10.

## 1 Service mapping

### Cancellation and rectification flows

Cancellation and rectification are independent. Neither requires nor causes the other. This mapping follows the merged SD-CANCEL01 design input; API contracts and implementation support still need qualification. REF-WITHDRAWAL; REF-CORRECTION.

[SPEC-SEI-022 combined Send / Correct / Cancel overview](invoice-sending/SPEC-SEI-022-invoice-sending-solution-summary.md#4-end-to-end-workflow) is the visual home for all three entry paths. The table below maps the cancellation and rectification journeys to their different API and SPFE interactions. [SPEC-SEI-023 entry actions](invoice-sending/SPEC-SEI-023-invoice-sending-logical-feature-specification.md#entry-actions) owns entry selection and safe next actions.

| Flow | Actor, condition and outcome | Sage / SPFE mapping and owning specifications |
|---|---|---|
| **Cancel e-invoice** | The issuer can request cancellation after full customer rejection when the operation did not take place. Rejection alone does not cancel the invoice. [SPEC-SEI-023 cancellation eligibility](invoice-sending/SPEC-SEI-023-invoice-sending-logical-feature-specification.md#proposed-cancel-eligibility) owns all state and reason conditions, including the separate treatment of technical and partial rejection. | Proposed issuer action on the existing resource → service **02 — `CancelInvoice`**. It carries a cancellation message, with no invoice UBL. Sending owns the request, response and recovery under [SPEC-SEI-024 §2.4](invoice-sending/SPEC-SEI-024-invoice-sending-sequence-and-reuse-assessment.md#24-proposed-withdrawal-interaction); [SPEC-SEI-029 proposed states](invoice-lifecycle/SPEC-SEI-029-invoice-lifecycle-logical-feature-specification.md#proposed-spain-invoice-states) owns the evidenced cancelled outcome. The existing lifecycle status POST has no qualified invoice-cancellation binding. |
| **Correct invoice — rectifying invoice** | The ERP creates a separately numbered rectifying invoice that references the original under [SPEC-SEI-015 IC-12](SPEC-SEI-015-invoice-creation-solution-specification.md#proposed-rectification-modify). The original issued content remains unchanged. The new invoice has its own acceptance, rejection and payment lifecycle. | Prepare the new invoice under SPEC-SEI-015, then use the sending flow: `POST {invoices}` and file upload → service **01 — `SendInvoice`** for the applicable original or public copy. [SPEC-SEI-043 sending contract and reuse assessment](invoice-sending/api-reference/SPEC-SEI-043-invoice-sending-api-reference.md#contract-baseline-and-reuse-assessment) owns API qualification. No separate `CorrectInvoice` SOAP service or new correction endpoint is selected. |

## 2 Customer and supplier roles

For normal sales and purchase flows, an ERP **supplier/purchase invoice** places the connected business in the buyer role and maps to `CustomerInvoiceEvents`. An ERP **customer/sales invoice** places it in the seller role and maps to `SupplierInvoiceEvents`. The service names identify the reporting party, not the ERP's invoice category. REF-EXAMPLES; REF-LIF.

For self-billing, preserve seller, buyer and material issuer separately under the [GLO-SEI-001 invoice definitions](../context/GLO-SEI-001-e-invoicing-terminology.md#invoices-representations-and-rules). The authenticated caller can represent a business; authentication alone does not grant buyer or seller authority.

Use [SPEC-SEI-041 input and XML field mapping](invoice-lifecycle/api-reference/SPEC-SEI-041-existing-e-invoice-lifecycle-api-reference.md#spfe-field-mapping) for saved invoice references and event dates, reasons and indicators. It also defines the conditions for full-payment reporting. Its eight-action table remains the single mapping authority; the supplied API leaves five action bindings unassigned. Open `statusAttributes` proves JSON schema flexibility, not Spain execution support. REF-LIF.

## 4 Evidence status

The manifest selects the locally reviewed **23 November 2026 PRE WSDL folder**. All nine WSDLs match the 29 October bytes; the README filename is corrected and UBL XSDs are now supplied. SPFE-S04–S08 originals were recovered under `context/archive` from Git, with their registered hashes unchanged. Newer examples at REF-EXAMPLES remain separate from those snapshots. Source registration does not qualify a production implementation. REF-BASELINE.

The example conflicts remain in [RES-SEI-002 specification impact](../context/RES-SEI-002-spain-public-platform-technical-evidence.md#spfe-example-review-and-specification-impact): buyer `PAYMENT` paired with seller wording, SOAP 1.1 event requests against SOAP 1.2 WSDLs, inconsistent dates, and download identity/correlation mismatches. Public Integration and the AEAT liaison need corrected fixtures and governing business schemas before executable conformance can be claimed. REF-EXAMPLES; REF-BASELINE.
