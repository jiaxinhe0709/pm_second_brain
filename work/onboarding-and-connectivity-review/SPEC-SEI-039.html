Customer Onboarding and Connectivity Sequence and Reuse Assessment

Summary — 037 · Customer paths — 038 · API and field changes — 040

Products: Sage 50, Sage 200, Sage Active and Sage X3 are the ERP products; Despachos is the accountant product. Each must meet the SXS and Tax integration precondition before enabling e-invoicing. SXS manages the product's datasetId / tenantId.

Revision overview — Phases 1–3

This view combines SPEC-SEI-021 and SPEC-SEI-036. It owns sequences, product impact and GAP decisions; 040 owns request/response examples. API/GAP IDs and predecessors are unchanged.

1 Engineering direction — Phases 1–3

What: set up Sage access to the customer's selected e-invoicing platform. Why: reuse valid setup without repeated registration or an unintended provider change.

Phase coverage: 1 — SPFE public solution; 2 — external private providers; 3 — Sage private-platform offering. Labels show analysis coverage, not delivery approval or confirmed API availability. REF-PHASE.

What exists: the shared E-Invoice API can list services, find connections, connect, read status and update supported details. Proposal: reuse these calls and the Tax certificate capability. Add Spain rules and provider support where needed. The supplied contracts establish API behaviour; they do not prove a Spain implementation is ready. FR-01–05; REF-TRUST.

3.1 Shared prerequisites — Phases 1–3

Start after the product has integrated SXS and Tax certificate management / Connections Service, as required by 038 §4. For each company, resolve its SXS dataset/client mapping first. If confirmed missing, complete qualified channel/SXS setup before dataset-scoped calls; an unavailable lookup remains pending. Then check NIF, permission and any required credential. Keep each credential/connection reference with its source API; their ID relationship remains unconfirmed under GAP-06. Provision only a genuinely missing credential through 040 §2. The diagram proposes the call order, not new SXS or B2B Tax contracts. GAP-01/03/06; REF-INTEGRATION; REF-TRUST; INT-CERT01–03; SPFE-S02.

Existing API-02 returns access-point entries with connection references. INT-AP01–06 describe one connection per datasetId / accessPointId pair and several addresses inside a connection. The 040 API-02 Spain mapping is an unvalidated BA hypothesis; GAP-02 owns the decision. Keep service-returned IDs; do not assume one access point or connection equals one platform. Public/private coexistence remains subject to implementation evidence under GAP-01/02/06. A saved connection does not activate a route. FR-02; INT-AP01–06; REF-CONNECTIONS.

3.4 Supported change — Phases 2–3, enabled changes only

The complete customer switch journey belongs to SPEC038. This section assesses its setup/API steps. Apply SPEC032 where old access or services end, within the same request. SPEC014 — Routing controls owns the effective routing change; do not create another switch process here.

Change routing or platform — ONB-S05/S06: read existing setup first. If the chosen Spain model exposes another platform as a different accessPointId, API-03 is the candidate for its missing dataset connection (§3.3). Other mappings require contract assessment under GAP-02. Within an existing connection, API-05 adds an address (add) or changes address dates (update), including both in one request. Confirm Spain address/grouping rules and public access-point representation. Separately authorise the routing change and confirm its effective start and earlier-invoice access. SPEC014 — Routing controls owns those controls. Private A to Private B stays disabled; PUT does not establish a general migration or rollback.

3.5 Uncertainty and recovery — Phases 1–3

Read the original connection before repeating an uncertain request. A failed or empty read does not prove no effect. While an address is RETRYING, observe it rather than submitting another connect. Keep unresolved work pending with an owner. INT-AP05/06. Recovery sequence.
